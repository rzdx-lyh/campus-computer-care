## 1 项目概述

### 1.1 项目背景
- 1.1.1 高校学生电脑持有率与故障发生频率
- 1.1.2 宿舍场景的特殊性：无备用机、断电断网、时间压力（作业/考试/答辩）
- 1.1.3 现有求助渠道的三重失效
  - 社交渠道（宿舍群、班级群）：回答碎片化、无责任主体、易传播错误操作
  - 搜索渠道：结果过时、SEO 广告多、不区分机型与系统版本
  - 官方渠道（信息中心报修）：排队周期长、只覆盖硬件维修、不覆盖"设置类"问题

### 1.2 问题定义
- 1.2.1 核心矛盾：排障知识存在，但**无法在正确的时间、以正确的粒度、给到正确的人**
- 1.2.2 三个具体缺口
  - 表达缺口：学生只会描述现象，不会描述故障
  - 信息缺口：缺少判断所需的关键条件（灯亮不亮、外接屏有没有画面）
  - 决策缺口：不知道哪一步有数据风险、什么情况必须停手
- 1.2.3 项目边界：做什么 / 不做什么（不做远程控制、不做硬件维修指导、不替代官方报修）

### 1.3 项目目标
- 1.3.1 业务目标：常见故障自助解决率、平均解决时长、误操作导致的数据丢失率
- 1.3.2 技术目标：故障条目 Top-1 命中率、平均追问轮次、端到端响应时延
- 1.3.3 可复制目标：知识库 schema 与学校解耦，换校只需替换网络认证与报修字段

### 1.4 项目范围与交付物
- 1.4.1 交付清单：知识库 JSON、诊断对话服务、管理后台、部署脚本、文档
- 1.4.2 不在本期范围：多模态识图、工单系统深度对接、跨校知识共享

### 1.5 术语与缩略语
- 六元组、条目（Entry）、槽位（Slot）、追问（Clarifying Question）、RAG、Top-1 命中率、紧急程度

## 2 需求分析

### 2.1 用户画像与使用场景
- 2.1.1 学生用户
  - 低年级：动手能力弱，需要"一步一动作"的引导
  - 高年级/研究生：需要原因解释与进阶方案（拆机、重装、双系统）
  - 留学生：中英文混合描述，术语不统一
- 2.1.2 宿舍网管 / 班级技术委员：需要快速判断"能不能现场解决"
- 2.1.3 信息中心运维人员：需要结构化的问题描述，减少来回沟通
- 2.1.4 典型场景故事（用户故事 + 时间线）
  - 场景 A：深夜赶课程设计，蓝屏后进不去系统
  - 场景 B：开学装机，WiFi 搜不到校园网
  - 场景 C：考试周线上考试前，笔记本风扇狂转、自动关机

### 2.2 功能需求（FR）
- FR-01 自然语言故障描述输入（支持错别字、口语、中英混合）
- FR-02 故障条目召回与置信度展示
- FR-03 多轮追问与快捷选项（是/否/不确定）
- FR-04 个性化排查步骤生成（按机型、系统版本、用户能力裁剪）
- FR-05 风险识别与强制提示（备份、停用、转人工）
- FR-06 排查进度记录与中断续接
- FR-07 知识库条目管理（增删改查、字段校验、版本发布）
- FR-08 反馈采集（解决了/没解决/解决到哪一步）
- FR-09 人工兜底与工单转交
- FR-10 管理端数据看板（高频故障、未命中问题、badcase）

### 2.3 非功能需求（NFR）
- 2.3.1 性能：首字响应 ≤ 2s，完整回答 ≤ 8s，支持开学季 200 并发
- 2.3.2 可用性：模型服务不可用时自动降级为规则引擎，核心链路可用性 ≥ 99.5%
- 2.3.3 安全与隐私：不读取用户文件、不索取账号密码、日志脱敏、会话可删除
- 2.3.4 可维护性：知识条目修改无需改代码、无需重新训练
- 2.3.5 可移植性：容器化部署，配置与知识分离
- 2.3.6 合规性：AI 生成内容标识、免责声明、未成年人保护

### 2.4 需求优先级与 MVP 划分
- 2.4.1 MoSCoW 分析（Must / Should / Could / Won't）
- 2.4.2 MVP 范围：单轮召回 + 固定追问 + 步骤输出 + 高风险提示
- 2.4.3 迭代路线：V1 可用 → V1.5 可维护 → V2 可运营

### 2.5 用例建模
- 2.5.1 用例图（学生 / 管理员 / 运维）
- 2.5.2 用例规约：主流程、备选流、异常流（描述无法识别、用户中途放弃、模型超时）
- 2.5.3 状态机：会话从"描述"到"结案"的状态迁移

## 4 AI 技术方案

### 4.1 知识表示：从经验文本到六元组
- 4.1.1 字段语义与写作规范（现象用学生原话、步骤用动词开头、原因按概率排序）
- 4.1.2 条目粒度设计：按"可区分的现象"切分，而非按"故障大类"切分
- 4.1.3 关键词体系：核心词、同义词、错别字、方言表达、英文缩写
- 4.1.4 紧急程度判定规则（数据风险 / 硬件损伤 / 安全隐患 / 时间敏感）

### 4.2 意图识别与条目召回
- 4.2.1 基线方案：关键词匹配 + 编辑距离，优点与天花板
- 4.2.2 语义召回：Embedding 模型选型、条目文本拼接策略
- 4.2.3 混合召回：BM25 + 向量 + 类型先验，加权打分公式
- 4.2.4 重排：用 LLM 对 Top-K 候选做相关性判别
- 4.2.5 置信度阈值与"未命中"策略（追问澄清 / 引导人工）

### 4.3 多轮追问策略
- 4.3.1 追问的本质：用最少的问题把假设空间缩到最小
- 4.3.2 信息增益排序算法与实现
- 4.3.3 槽位设计：电源状态、显示输出、网络环境、近期变更、数据重要性
- 4.3.4 终止条件：信息足够 / 命中高风险 / 用户显式拒绝 / 达到轮次上限
- 4.3.5 话术设计：一次只问一个点、给选项、允许"不确定"

### 4.4 排查方案生成
- 4.4.1 受约束生成：只允许使用条目内的步骤，禁止模型自由补充
- 4.4.2 个性化裁剪：按机型（可拆电池/不可拆）、系统（Win10/11/macOS）、用户能力分层
- 4.4.3 输出结构：结论置信度 + 分步动作 + 每步预期现象 + 风险提示
- 4.4.4 失败分支：某步无效时如何跳到下一条目

### 4.5 安全、幻觉与兜底
- 4.5.1 高风险硬规则（硬盘不识别、电池鼓包、进液、异味、接口发烫）
- 4.5.2 数据保护优先原则：先备份、后操作
- 4.5.3 幻觉抑制：引用溯源、字段白名单、输出校验器
- 4.5.4 提示词注入与越权防护
- 4.5.5 降级链路：模型超时/限流 → 规则引擎 → 静态 FAQ

### 4.6 效果评估
- 4.6.1 评测集构建：200 条真实学生提问（含口语、错别字、信息缺失）
- 4.6.2 指标定义：Top-1/Top-3 命中率、平均追问轮次、步骤可执行率、风险召回率、人工兜底率
- 4.6.3 评估方法：离线评测 + 人工双盲评审 + 线上 A/B
- 4.6.4 badcase 归因分类（表达问题 / 知识缺失 / 检索错误 / 生成越界）

### 4.7 成本与延迟优化
- 4.7.1 小模型分流：简单意图用小模型，复杂诊断用大模型
- 4.7.2 缓存：高频问题答案缓存、Embedding 缓存
- 4.7.3 流式输出与首字时延优化
- 4.7.4 单次诊断 token 成本测算

## 5 核心功能实现

### 5.1 故障自诊对话
- 5.1.1 会话状态机实现（IDLE → RECALL → CLARIFY → GUIDE → CLOSE）
- 5.1.2 首轮理解：文本清洗、口语归一化、实体抽取
- 5.1.3 追问卡片：快捷选项、跳过、补充描述
- 5.1.4 步骤清单：勾选完成、上一步/下一步、卡住求助
- 5.1.5 多故障并发处理（如"蓝屏 + WiFi 连不上"）

### 5.2 知识库管理后台
- 5.2.1 条目 CRUD 与表单校验（字段长度、枚举、必填）
- 5.2.2 版本管理与灰度发布（草稿 / 审核 / 上线 / 回滚）
- 5.2.3 去重与冲突检测（相似条目提示合并）
- 5.2.4 批量导入导出（Excel ↔ JSON）
- 5.2.5 权限与操作审计

### 5.3 风险分级与转人工
- 5.3.1 紧急程度计算：条目基础分级 + 上下文修正（如"论文没备份"上调）
- 5.3.2 转人工触发条件与提示话术
- 5.3.3 工单字段设计（现象、已尝试步骤、设备信息、联系方式）
- 5.3.4 与校园报修系统的对接方式（API / 邮件 / 二维码）

### 5.4 反馈闭环
- 5.4.1 结果采集：解决了 / 没解决 / 解决了但有小问题
- 5.4.2 未解决问题聚类，反哺知识库新增条目
- 5.4.3 条目质量评分（解决率、平均轮次、差评率）
- 5.4.4 周期性知识评审机制

### 5.5 多端适配与体验细节
- 5.5.1 移动端优先的排版与长步骤折叠
- 5.5.2 弱网与断线重连
- 5.5.3 无障碍与大字模式

### 5.6 关键实现难点
- 5.6.1 混合召回的分数归一化
- 5.6.2 追问决策的冷启动（无历史数据时如何排序）
- 5.6.3 多轮上下文压缩与指代消解
- 5.6.4 关键代码片段与性能数据

## 7 总结与展望

### 7.1 项目成果
- 7.1.1 交付物清单与完成度
- 7.1.2 量化指标达成情况（对照 1.3 的目标）
- 7.1.3 用户反馈与典型案例

### 7.2 不足与反思
- 7.2.1 知识覆盖的边界：非常见故障、新硬件、macOS/Linux 支持不足
- 7.2.2 模型误判的不可完全消除
- 7.2.3 隐私与合规的持续压力
- 7.2.4 运营依赖：知识库需要人持续维护

### 7.3 演进路线
- 7.3.1 短期（1–3 个月）：多模态输入，拍照识别蓝屏代码与花屏形态
- 7.3.2 中期（3–6 个月）：对接报修与资产系统，形成"自助—工单—维修—回访"闭环
- 7.3.3 长期（6–12 个月）：跨校知识联盟、故障预测（按机型/批次预警）
- 7.3.4 技术演进：小模型端侧推理、知识图谱化

### 7.4 可复制性总结
- 7.4.1 "结构化知识 + 受约束生成"范式的迁移价值
- 7.4.2 可迁移场景：校园网自助、实验室设备报修、宿舍水电报修
