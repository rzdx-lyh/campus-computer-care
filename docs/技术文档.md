# 1. 项目概述

## 1.1 项目背景

高校宿舍中的电脑故障具有高频、分散、表达不专业和处理时间紧的特点。学生通常只能用“黑屏”“蓝屏”“很卡”“连不上网”等现象描述问题，难以提供电源状态、错误码、外接屏结果等关键条件。群聊、搜索引擎和短视频平台虽然能提供答案，但存在信息碎片化、版本过期、广告干扰和误操作风险。

学校维修渠道更偏向硬件维修和线下排队，对网络认证、驱动冲突、散热积灰等常见问题缺少第一时间的结构化问诊。学生需要重复描述问题，维修员也需要重新确认背景，整体沟通成本较高。

校园电脑管家面向这一真实场景，构建“设备体检 → 多轮 AI 问诊 → 本地知识检索 → 一键报修 → 维修建议 → 维修评价 → 管理洞察”的闭环。

## 1.2 项目目标

1. 让学生用自然语言完成故障描述，不要求掌握专业术语。
2. 通过多轮追问补齐关键条件，避免模型在信息不足时直接下结论。
3. 以本地 25 条故障知识为基础，提供可追溯的 RAG 诊断依据。
4. 输出结构化、可执行的排查步骤，并明确安全边界。
5. 将诊断结果直接转换为维修工单，减少重复填写。
6. 为维修员提供 AI 维修摘要，为管理员提供统计和运维洞察。
7. 在没有网络时仍可打开知识图谱和本地知识。

## 1.3 目标用户

- 学生：自助排查、语音问诊、报告导出、提交工单和评价。
- 维修员：接单、AI 维修建议、维修记录、完成工单。
- 管理员：状态统计、故障类型分析、AI 洞察和 CSV 导出。

## 1.4 当前边界

- 数据使用 LocalStorage / sessionStorage，定位为课程设计和赛事演示。
- 账号鉴权为演示级实现，账号来自代码默认值并可由环境变量覆盖，尚未接入学校统一身份认证。
- 联网 Search + Fetch 默认关闭。
- 学生知识库使用进程内 RAG；维修员特供资料库使用本地持久化向量库 `data/vector-db.json`，重启后保留。
- 浏览器内录制视频为 WebM；赛事提交版另提供 5 分 01 秒、1080p 的 MP4 演示视频。

# 2. 需求分析

## 2.1 学生需求

| 需求 | 解决方式 |
| --- | --- |
| 不知道如何描述故障 | 自然语言聊天、语音输入、快捷问题 |
| 信息不足时无法判断 | AI 返回追问问题，学习模式逐题引导 |
| 不信任 AI 结论 | 展示知识库/网页来源、置信度和匹配关键词 |
| 排查步骤不清晰 | 结构化原因、步骤、风险等级和安全提示 |
| 报修重复填写 | 诊断结果生成工单草稿并自动预填 |
| 维修后无法反馈 | 已完成工单支持 1–5 星与一句话评价 |

## 2.2 维修员需求

维修员需要快速理解故障历史，而不是只看一句“电脑坏了”。系统提供工单标题、描述、优先级、预约时间、维修记录和 AI 维修建议。AI 建议包含一句话判断、可能原因、建议备件或工具、预计工时、维修与验收步骤。维修员登录后还可以使用特供资料库进行本地向量检索、播放图文/视频课件，并上传工单统计与明细。

## 2.3 管理员需求

管理员需要从工单中看到趋势，而不是逐条阅读。系统提供总数、待接单、维修中、完成率、故障类型柱状图、最近工单、平均评分和 AI 运维洞察，并可查看维修员上传的后台数据。

## 2.4 非功能需求

- 流式输出，避免长等待。
- 无 Key 或模型失败时不影响页面使用。
- 移动端布局可用。
- API Key 仅在服务端。
- 不鼓励学生自行拆机。
- 诊断依据可展示、可导出、可离线查看。

## 3.1 总体架构

```mermaid

  U["浏览器页面"] --> N["Next.js App Router"]
  N --> D["/api/diagnose"]
  N --> R["/api/repair-advice"]
  N --> I["/api/insight"]
  D --> K["本地知识库"]
  D --> V["哈希向量库"]
  D --> W["Search + Fetch（可选）"]
  D --> M["DeepSeek deepseek-flash"]
  R --> M
  I --> M
  U --> L["LocalStorage / sessionStorage"]
  U --> P["PWA / Service Worker"]
```

> 最新版本还包含 `/api/auth/login`、`/api/auth/session`、`/api/technician/knowledge` 和 `/api/repair-reports` 等接口。

## 3.2 分层说明

- 表现层：React Server/Client Components + Tailwind。
- API 层：多组 Node.js Route Handlers，包括诊断、维修建议、管理洞察、鉴权、维修员资料库和上传记录。
- AI 编排层：角色 Prompt、对话历史、知识检索、JSON 解析和降级。
- 数据层：LocalStorage 工单、sessionStorage 诊断草稿。
- 离线层：Manifest、Service Worker、离线兜底页。
- 浏览器能力层：语音、报告、SVG、Canvas 视频。

## 3.3 目录分层

`src/app` 负责路由和页面；`src/components` 负责可复用 UI；`src/lib` 负责类型、存储、知识检索和浏览器能力；`knowledge-base` 保存结构化知识；`tests` 保存核心测试；`docs` 保存交付材料。

# 4. AI 技术方案

## 4.1 模型选型理由

项目选择 DeepSeek `deepseek-flash` 作为主诊断模型。选择依据不是“参数越大越好”，而是校园 IT 服务场景下的准确性、响应速度、成本、可解释性与工程可维护性。

| 方案 | 主要优势 | 主要局限 | 本项目结论 |
| --- | --- | --- | --- |
| DeepSeek API `deepseek-flash` | 中文理解较好、支持流式输出、兼容 OpenAI SDK、成本可控 | 依赖外部网络与模型服务 | **采用**，作为诊断、维修建议和管理洞察的主模型 |
| 本地小参数模型 | 数据不出本机、离线可运行 | 部署体积大，中文长尾故障诊断和结构化输出稳定性较弱 | 不作为主模型 |
| 监督微调模型 | 可针对固定任务定制 | 知识更新慢、样本和维护成本高，不利于展示知识来源 | 不采用，优先 RAG |

项目没有选择微调，主要原因是校园故障知识会持续更新，而 RAG 可以把“模型能力”和“校园知识”解耦：知识库更新后无需重新训练模型，诊断结果还能展示来源、匹配关键词和置信度，便于评审验证与后续维护。

## 4.2 AI 系统集成方式

AI 能力通过服务端 Route Handler 集成，不把 API Key 暴露给浏览器。核心链路如下：

1. 前端提交故障描述、最近对话历史和当前角色。
2. `/api/diagnose` 在服务端读取 `DEEPSEEK_API_KEY`、`DEEPSEEK_BASE_URL` 和 `DEEPSEEK_MODEL`，通过 `openai` SDK 调用兼容接口。
3. 服务端并行准备本地知识命中、向量 RAG 结果和可选联网证据。
4. 系统 Prompt 把角色、对话、证据和安全边界组合成上下文，要求模型返回结构化 JSON。
5. 模型响应以流式方式返回，前端通过增量事件逐字渲染，避免长时间白屏。
6. 后端清洗 Markdown 围栏、校验字段并转换为前端类型；解析失败或网络异常时返回可用的降级结果。

```mermaid
flowchart LR
  U["学生 / 维修员 / 管理员"] --> P["Next.js 页面"]
  P --> A["服务端 API"]
  A --> K["25 条本地知识"]
  A --> R["384 维哈希向量 RAG"]
  A --> S["Search + Fetch（可选）"]
  A --> M["DeepSeek API"]
  M --> J["结构化 JSON / 流式事件"]
  J --> P
```

集成层同时覆盖三类 AI 任务：故障诊断、维修建议和管理洞察。三者共用模型与环境变量，但使用不同系统 Prompt、输入结构和输出字段，避免把同一个 Prompt 强行复用到所有角色。

## 4.3 多轮问诊与上下文控制

系统要求模型输出“信息是否充分”和“追问问题”。前端保留最近 8 条对话，后端限制单条历史 2000 字符、当前描述 500 字符。Prompt 要求最多引导补充 2 轮，不重复询问已回答内容。

```mermaid
stateDiagram-v2
  [*] --> 采集
  采集 --> 判断
  判断 --> 追问: 信息不足
  追问 --> 采集: 用户回答
  判断 --> 生成: 信息充分
  生成 --> 结果
  判断 --> 降级: 模型异常
  降级 --> 结果
  结果 --> [*]
```

这种设计把“问诊”实现为可控状态机，而不是无限聊天：信息不足时只追问影响定位的关键条件；信息足够时才输出完整原因、步骤和建议；模型故障时仍返回安全排查建议，并明确标记为降级结果。

## 4.4 本地知识与混合 RAG

知识库包含 25 条六元组故障知识，每条覆盖故障类型、现象关键词、追问问题、可能原因、排查步骤和紧急程度。

```json
{
  "故障类型": "蓝屏",
  "现象关键词": ["蓝屏", "重启"],
  "追问问题": ["能否看到错误码？"],
  "可能原因": ["驱动冲突"],
  "排查步骤": ["记录错误码"],
  "紧急程度": "高"
}
```

检索采用“关键词召回 + 轻量向量召回”的混合策略：

- 关键词检索对故障类型和现象关键词进行精确包含与字符重合度打分。
- 为避免“电脑卡”误命中“电脑很烫”，只接受评分不低于 8 的高置信候选。
- 字符 unigram、bigram、trigram 经 FNV-1a 哈希映射到 384 维向量，再进行归一化和余弦相似度计算。
- 长文本按约 700 字分块、100 字重叠，默认返回 Top-5 片段，并过滤相似度过低的噪声。
- 证据片段携带来源类型、URL、标题和相关性，供前端展示证据链。

```mermaid
flowchart LR
  T["故障知识 / 网页正文"] --> C["700 字分块"]
  C --> E["字符 n-gram 哈希向量"]
  Q["用户问题"] --> E
  E --> S["余弦相似度排序"]
  S --> R["Top-5 证据片段"]
  R --> P["诊断 Prompt"]
```

## 4.5 联网 Search + Fetch

设置 `DEEPSEEK_WEB_SEARCH=true` 后，系统启用可选联网增强：

1. 调用 `/v1/tools/search` 搜索 6 条结果。
2. 过滤相关性低于 0.45、标题过短或无标题的页面。
3. 最多选择 2 条，调用 `/v1/tools/fetch` 获取 Markdown 正文。
4. 清洗正文并加入向量库。
5. 仅把高相关网页片段注入 Prompt，并保留本地知识作为兜底。

联网默认关闭，原因包括搜索结果质量存在波动、Search/Fetch 按成功请求计费，以及赛事演示更强调可重复和可控。

## 4.6 角色 Prompt 与结构化输出

- 学生：亲切、少术语、安全优先，输出可直接照做的步骤。
- 维修员：给出专业原因、备件、工时和验收标准。
- 管理员：给出影响范围、处理优先级、资源调度和预防建议。

模型只输出 JSON，后端同时保留中文字段和前端使用的英文字段。若返回 Markdown 围栏，会先清洗再解析；字段缺失时使用类型转换和默认值补齐，保证页面不会因单个字段异常而崩溃。

## 4.7 性能、成本与稳定性优化策略

| 优化维度 | 具体策略 | 目的 |
| --- | --- | --- |
| 响应速度 | 流式输出、前端增量渲染 | 降低等待感，长回答更早可见 |
| 上下文成本 | 只保留最近 8 条对话；历史单条最多 2000 字；当前描述最多 500 字 | 控制 Token 成本，减少无关上下文 |
| 检索准确性 | 关键词阈值 8、向量 Top-5、相似度过滤、错误码上下文注入 | 提高召回质量并减少误命中 |
| 证据可解释 | 同时展示知识来源、关键词、置信度和网页链接 | 让 AI 结论可追溯、可复核 |
| 联网成本 | 默认关闭；最多 Fetch 2 个高相关页面 | 避免无意义搜索和费用波动 |
| 输出稳定性 | JSON 清洗、字段规范化、流中断保留已输出内容 | 避免格式异常导致页面不可用 |
| 故障可用性 | 无 Key、模型失败、联网失败均返回降级结果 | 保证核心流程仍可演示 |
| 离线体验 | PWA、Service Worker、本地知识图谱缓存 | 网络不可用时仍能查看知识 |

## 4.8 安全边界与降级策略

- API Key 仅存在于服务端环境变量，不进入浏览器打包产物。
- 涉及拆机、断电、进液或硬件操作时，Prompt 强制提醒“先断电，注意安全”，不鼓励学生自行拆机。
- 无 Key：返回 `error + result`，页面显示兜底结果。
- 非标准 JSON：记录原始文本并返回降级诊断。
- 流中断：保留已输出内容并追加兜底。
- 联网失败：继续使用本地知识。
- 兜底标记：`degraded=true`、`informationSufficient=false`、`needRepair=true`。

# 5. 核心功能实现

## 5.1 首页与设备体检

首页提供体检和 AI 诊断入口。体检页读取浏览器公开能力，并在不支持时显示“浏览器未开放”，不把浏览器限制等同为硬件故障。

## 5.2 诊断页

诊断页包含文字输入、语音识别、快捷问题、学习模式、错误码提示、流式消息、证据卡、追问、报告、朗读、视频和工单入口。

## 5.3 工单与评价

工单状态为 `pending → repairing → completed`。学生可提交宿舍、设备、描述、照片 Base64、预约时间。完成后可写入 1–5 星和一句话评价。

## 5.4 维修员与管理员

维修员可以接单、请求 AI 维修建议、填入维修记录并完成。管理员可查看统计、生成 AI 洞察和导出带 UTF-8 BOM 的 CSV。

## 5.5 知识图谱

`/graph` 使用纯 SVG 展示故障类型、知识条目、现象和原因。任意节点带 `q` 参数跳转诊断页，页面读取 URL 后预填输入框。

## 5.6 PWA 离线

Manifest 提供安装信息和 192/512 图标。Service Worker 预缓存首页、图谱、诊断、体检、Manifest、离线页和静态 JS/CSS。导航 network-first，静态资源 cache-first，API 不缓存。

---

## 5.7 账号鉴权与角色守卫

系统新增登录页和服务端鉴权接口。维修员、管理员通过账号密码登录，服务端使用 scrypt 加盐哈希和常量时间比较校验口令，成功后签发 HMAC 会话令牌。前端通过 AuthContext 和 RoleGate 控制页面入口，令牌默认 8 小时有效。默认账号可由环境变量覆盖，生产环境必须替换。

## 5.8 维修员特供资料库与本地向量库

维修员资料库包含维修图文资料和可播放的视频课件。`local-vector-db.ts` 使用哈希嵌入与余弦相似度检索，索引持久化到 `data/vector-db.json`，删除后可由种子数据自动重建。该功能提升了维修知识与一线经验复用能力。

## 5.9 工单 AI 诊断与后台数据上传

AI 诊断不仅能在独立诊断页使用，也收敛到具体工单：维修员和管理员可从工单上下文发起 AI 辅助诊断，结果与工单设备、描述和历史信息关联。维修员可一键上传统计与明细，管理员在看板查看上传记录。

## 5.10 数字人与校园就近派单

数字人“小管家”使用 SVG 表情随诊断进度变化，能以气泡展示结论并一键朗读。学生提交工单时，系统按宿舍楼宇在 SVG 校园地图上推荐最近空闲维修员并估算到场时间，增强校园场景的交互体验。

## 5.12 API 契约摘要

# 8. 创新点

## 8.1 技术创新点

1. **混合检索增强诊断**：关键词高置信召回与 384 维字符 n-gram 向量检索并行，兼顾校园短文本精确命中与长尾表达泛化。
2. **证据驱动的结构化诊断**：模型输出与本地知识、联网来源、匹配关键词、相关性分数一起呈现，突破传统聊天机器人的“黑盒回答”。
3. **多轮问诊状态机**：把“信息是否充分—追问—再判断—生成结论”实现为受控流程，并限制追问轮数与上下文长度。
4. **错误码上下文注入**：自动识别 `0x0000007B`、`INACCESSIBLE_BOOT_DEVICE` 等代码，从知识库生成错误码映射并注入 Prompt。
5. **角色化 Prompt 编排**：同一模型按学生、维修员、管理员切换专业深度、输出字段和安全边界。
6. **可降级的 AI 工程链路**：无 Key、格式异常、流中断和联网失败均能返回可用兜底结果，保证演示与真实使用连续性。
7. **轻量零外部向量库 RAG**：无需额外向量数据库即可完成索引、检索和证据展示，降低课程部署与比赛演示成本。
8. **服务端鉴权与角色守卫**：口令使用 scrypt 加盐哈希，会话令牌使用 HMAC 签名，敏感逻辑不进入前端。

## 8.2 应用创新点

1. **诊断到报修的连续体验**：诊断结论可一键生成工单草稿，自动预填标题、描述、设备类型和优先级，避免重复录入。
2. **学生学习模式**：把追问转换为“步骤 1/N”卡片，支持上一步、下一步和逐题回答，降低非专业用户的理解负担。
3. **诊断证据链与报告导出**：学生可查看来源、关键词、置信度，并导出包含免责声明的 Markdown 诊断报告。
4. **AI 维修协同闭环**：从学生诊断延伸到维修员 AI 建议、维修记录、完成评价和管理端洞察。
5. **维修员特供资料库**：维修员登录后可检索图文/视频课件，并持续补充资料，形成可运营的校园维修知识资产。
6. **校园就近派单**：提交工单时按宿舍楼宇在校园地图上推荐最近空闲维修员，并估算到场时间。
7. **管理端运维洞察**：聚合工单状态、故障类型、评分和 AI 建议，支持 CSV 导出，为校园 IT 服务提供数据依据。
8. **离线知识入口**：网络不可用时仍可打开知识图谱和 25 条本地故障知识，兼顾弱网场景。

## 9.3 后续规划

1. 接入学校统一身份认证、生产级 RBAC 和服务端数据库。
2. 知识库后台 CRUD、版本管理和审核流程。
3. 真实向量数据库与混合检索评估。
4. 图片/截图 OCR 和多模态诊断。
5. 工单通知、维修排班、备件库存和 SLA。
6. AI 质量评测集、成本监控和调用日志。
7. 公网部署、在线演示链接与压力测试（5–8 分钟 MP4 演示视频已完成，见交付材料）。


## 9.4 风险边界与应对

| 风险 | 当前状态 | 应对 |
| --- | --- | --- |
| 浏览器存储丢失 | 工单和草稿保存在 LocalStorage | 正式版迁移服务端数据库，并提供导出 |
| 演示口令弱 | 默认 admin/tech 账号可由环境变量覆盖 | 生产部署必须替换并接入统一身份认证 |
| 联网结果波动 | Search + Fetch 默认关闭 | 仅在需要时开启，展示来源并保留本地知识兜底 |
| 模型格式异常 | 后端清洗围栏并解析 JSON | 解析失败返回 degraded 结果，前端显示降级横幅 |
| 资料检索规模 | 本地向量库适合演示与单机 | 生产升级向量数据库、增量索引和权限过滤 |
| 视频与语音兼容 | 依赖浏览器能力 | 不支持时隐藏或提示，保留文字输入和脚本演示 |

## 9.5 总结与展望

校园电脑管家不是单次大模型问答，而是把多轮问诊、知识检索、结构化输出、证据展示、鉴权、工单闭环、维修资料库、数字人交互、校园派单和离线能力组合成可解释、可降级、可演示的工程方案。当前版本适合赛事展示和课程验收；下一阶段应重点补齐生产级数据库、统一身份认证、自动化 E2E、公网部署和压力测试。
