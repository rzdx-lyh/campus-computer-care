# 校园电脑管家答辩 Q&A

## 一、AI 技术深度（35%）

### Q1：为什么选择 DeepSeek？

DeepSeek 中文能力适合校园问答，OpenAI 兼容接口接入成本低，支持流式输出和 JSON Output；`deepseek-flash` 的成本和响应速度适合高频诊断。我们还保留了 Search + Fetch 作为可选的网页增强能力。

### Q2：为什么采用 RAG，而不是直接让大模型回答？

直接回答缺少可验证依据，也容易受模型知识过期影响。RAG 从 25 条本地知识中召回相关条目，把追问、原因和步骤注入 Prompt，并在前端展示来源与置信度，回答更可控、更可解释。

### Q3：为什么不用微调？

故障知识会持续更新，微调需要重新训练和评估，成本高；RAG 可以直接更新 JSON，便于老师审核和学校本地化。比赛场景更看重知识来源、检索证据和工程闭环，而不是训练一个更大的模型。

### Q4：你们的 RAG 向量库怎么实现？

使用字符 unigram、bigram、trigram 特征，通过 FNV-1a 哈希映射到 384 维向量，归一化后用余弦相似度检索。内容按约 700 字分块、100 字重叠。它不依赖外部向量数据库，适合课程部署和现场演示。

### Q5：为什么没有使用真正的 Embedding 模型？

当前项目不新增外部依赖，也没有稳定的 Embedding API 预算。哈希向量对中文关键词和局部表达已经有较好召回，且完全离线可复现。生产版可以替换为专业 Embedding + 向量数据库。

### Q6：多轮问诊如何避免模型乱问？

System Prompt 明确要求不重复历史已回答信息，最多引导补充 2 轮，并要求输出“信息是否充分”和“追问问题”。前端学习模式一次只展示一个问题，用户回答后再次携带历史请求。

### Q7：如何保证结构化输出？

Prompt 要求只输出 JSON，并规定故障摘要、原因、步骤、紧急程度、建议、是否报修、信息是否充分和追问问题。后端清理 Markdown 围栏、解析 JSON、规范化字段；解析失败时返回降级结果。

### Q8：模型失败时系统会怎样？

无 Key、请求失败、JSON 异常或流中断时，后端返回可解析的 `error + result`。兜底结果标记 `degraded=true`，页面显示降级横幅，仍给出安全建议和报修入口，不会卡在三个点。

### Q9：为什么有时诊断需要 20 秒？

开启联网 Search + Fetch 时会产生搜索、页面抓取和模型生成多个网络阶段；默认关闭联网后，主要耗时来自模型本身。系统先发送本地知识命中的进度 delta，降低首字等待感，并允许用户先看到状态。

### Q10：为什么角色 Prompt 不放在前端？

角色 Prompt 放在服务端可避免被用户篡改，也便于统一版本管理。前端只传角色枚举，服务端规范化后拼接学生、维修员或管理员上下文。

## 二、创新性与产品设计（25%）

### Q11：项目最有创新性的地方是什么？

不是单独做聊天机器人，而是把“诊断证据、学习模式、错误码上下文、一键工单、维修建议、维修评价和管理洞察”串成闭环，让 AI 结果真正进入学校维修流程。

### Q12：学习模式解决什么问题？

普通追问会一次展示多个问题，学生容易遗漏。学习模式把追问变成步骤 1/N，提供上一步和下一步，一次只处理一个问题，降低认知负担。

### Q13：错误码识别为什么不直接交给模型？

前端先识别错误码并映射到知识库故障类型，可以把确定性的上下文显式传给模型，减少模型漏看或误判；同时用户能立刻看到系统识别结果。

### Q14：知识图谱有什么价值？

它把故障类型、知识条目、现象和原因可视化，用户可以浏览知识关系，点击节点直接带着问题进入诊断。纯 SVG 不依赖第三方图库，离线也能显示。

### Q15：一键工单会不会替用户做决定？

不会。系统只生成工单草稿并预填描述、设备和优先级，最终由学生确认宿舍、预约时间和提交动作。AI 判断需要报修时也会提供人工入口。

### Q16：维修评价有什么意义？

评价把服务结果反馈到工单列表、维修员工作台和管理员看板，形成服务质量指标，为后续排班、培训和资源调度提供依据。

## 三、工程质量（10%）

### Q17：项目如何做质量保障？

使用 TypeScript 严格模式、`npm run typecheck`、8 条 Node Test Runner 测试、GitHub Actions 的 install → typecheck → test → build 流程，并在提交前检查 Service Worker 语法。

### Q18：为什么测试里专门测负样本？

RAG 系统不仅怕召回不到，更怕错误召回。例如“电脑卡”曾可能误命中“电脑很烫”，我们提高最低评分阈值，并用负样本测试防止回归。

### Q19：为什么没有服务端数据库？

这是赛事演示版，需求明确允许 LocalStorage。使用浏览器存储可以快速验证交互和闭环，但也清楚标注了无登录、无审计、换设备丢失等限制。

### Q20：PWA 离线范围是什么？

预缓存首页、知识图谱、诊断页、体检页、Manifest、离线页和静态 JS/CSS。API 不缓存，AI 需要联网；离线时导航回退缓存页或 offline.html。

### Q21：如何处理浏览器能力不兼容？

语音识别和语音播报在不支持时隐藏或提示；视频生成在 MediaRecorder 不支持时提示使用 Chrome/Edge；体检字段不支持时显示“浏览器未开放”。

## 四、数据、隐私与安全

### Q22：知识库数据从哪里来？

知识库由校园常见故障场景、通用排障实践和学校网络认证场景整理而成，采用六元组结构，包含 25 条知识和 125 个现象关键词。正式上线前应由学校信息中心审核。

### Q23：API Key 如何保护？

API Key 只从服务端环境变量读取，进入 `.gitignore` 的本地文件不提交；提交前使用 Key 前缀扫描检查。浏览器代码、public 目录和截图中都不包含密钥。

### Q24：用户数据会泄露吗？

设备体检只在浏览器读取；工单和评价保存在 LocalStorage；联网检索默认关闭。开启联网时，故障描述会发送到 DeepSeek Search，正式版应增加脱敏、用户告知和数据删除机制。

### Q25：AI 建议会不会误导学生？

所有结果带免责声明，Prompt 明确禁止建议学生自行拆机；涉及进液、焦糊味、冒烟时必须先断电和转专业维修。AI 只做初步判断，不替代维修员现场检测。

## 五、社会价值与商业化

### Q26：项目的社会价值是什么？

它能降低学生误操作和数据丢失风险，缩短常见故障响应时间，把真正需要维修的问题更快送到维修员手中，同时沉淀学校自己的故障知识资产。

### Q27：如何推广到其他学校？

知识库 schema 与学校解耦，只需替换校园网认证方式、宿舍信息和报修流程；前端和后端可独立部署，后续接入学校统一身份认证与工单系统。

### Q28：商业化路径是什么？

可作为校园 IT 服务台 SaaS，按校区、设备规模或知识库维护服务收费；也可与资产管理系统、备件库存、维修排班和 SLA 监控组合。

## 六、现场演示风险应答

### Q29：如果现场网络不可用怎么办？

PWA 可离线打开知识图谱和本地 25 条故障知识；AI 部分会显示离线提示和可读错误，不会让页面崩溃。正式演示前会准备线上环境和服务端 Key。

### Q30：如果模型返回格式错误怎么办？

服务端会清理代码围栏、尝试提取 JSON；仍失败时返回 `degraded=true` 的结构化兜底结果，页面继续显示建议与报修入口。
